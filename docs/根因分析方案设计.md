> **实施状态**: 本文档为设计方案，详细实施计划见 [根因分析实现计划](./plans/2026-03-22-根因分析实现计划.md)

## 1. 现状问题

### 1.1 现有分析结论的问题

从获取的故障复盘数据来看，现有分析大量归因为：
- **研发环节**：「正常场景遗漏」「异常场景遗漏」「边界条件未覆盖」
- **测试环节**：「关联场景考虑不全」「测试用例覆盖不全」

### 1.2 问题本质

这些归因**过于泛化**，存在以下问题：

| 泛化归因 | 存在的问题 |
|---------|-----------|
| 场景考虑不全 | 1. 什么场景没考虑？<br>2. 为什么没考虑到？<br>3. 如何避免下次不再遗漏？ |
| 测试覆盖不全 | 1. 哪些用例漏了？<br>2. 是设计问题还是执行问题？<br>3. 如何补充？ |
| 代码逻辑错误 | 1. 错误根因在哪？<br>2. 为什么没在代码review发现？<br>3. 需要如何重构？ |

**核心问题**：归因到"场景考虑不全"后，**没有进一步追问**：
- 为什么这个场景没考虑到？
- 是设计阶段的问题？编码阶段的问题？还是测试阶段的问题？
- 具体是哪个环节的checklist或流程缺失？
- 改进措施如何落地？

## 2. 根因分析设计思路

### 2.1 核心理念：从"场景不全"到"根因挖掘"

```
故障现象
    ↓
问题分类（开发引入 / 测试泄露 / 需求变更 / 外部依赖）
    ↓
初步归因（如：正常场景遗漏）
    ↓ 【关键】继续追问"为什么"
    ↓
深层根因（设计缺陷 / 编码失误 / 流程缺失 / 规范不完善）
    ↓
可落地的改进措施
```

### 2.2 根因分析层次模型

```
┌─────────────────────────────────────────────────────────────────┐
│ 第一层：现象描述                                                  │
│   - 故障现象是什么？                                               │
│   - 影响范围？严重程度？                                          │
├─────────────────────────────────────────────────────────────────┤
│ 第二层：问题分类                                                  │
│   ├─ 开发引入（代码问题、设计问题）                                 │
│   ├─ 测试泄露（用例设计问题、用例执行问题）                          │
│   ├─ 需求变更（需求描述不清、需求确认不到位）                        │
│   └─ 外部依赖（第三方服务、基础设施）                              │
├─────────────────────────────────────────────────────────────────┤
│ 第三层：初步归因（来自现有系统，可作为参考）                          │
│   - 正常场景遗漏 / 异常场景遗漏 / 边界条件未覆盖                      │
│   - 关联场景考虑不全 / 测试路径覆盖不全                              │
├─────────────────────────────────────────────────────────────────┤
│ 第四层：深层根因（核心改进点）★★★★★                                  │
│   ├─ 1. 设计层面                                                    │
│   │     ├─ 设计文档缺失或评审不到位                                   │
│   │     ├─ 接口契约定义不清晰                                        │
│   │     └─ 数据模型/状态机设计有疏漏                                 │
│   ├─ 2. 编码层面                                                    │
│   │     ├─ 代码走查流于形式                                          │
│   │     ├─ 防御性编程不足                                            │
│   │     └─ 异常处理不完善                                            │
│   ├─ 3. 测试层面                                                    │
│   │     ├─ 测试用例设计方法论缺失                                    │
│   │     ├─ checklist不完善                                           │
│   │     ├─ 场景组合/状态转换覆盖不足                                  │
│   │     └─ 测试数据准备不充分                                        │
│   ├─ 4. 流程层面                                                    │
│   │     ├─ 设计阶段缺少专家评审                                      │
│   │     ├─ 代码合入缺少强制review                                     │
│   │     └─ 发布前缺少冒烟测试                                        │
│   └─ 5. 知识管理层面                                                 │
│         ├─ 类似问题复盘未形成checklist                                │
│         ├─ 经验传承机制缺失                                          │
│         └─ 新人培训不系统                                            │
├─────────────────────────────────────────────────────────────────┤
│ 第五层：可落地的改进措施（★★★★★）                                    │
│   ├─ 直接改进（具体可执行）                                          │
│   │     ├─ 补充XXX场景的测试用例                                      │
│   │     ├─ 新增代码走查checklist第X条                                 │
│   │     ├─ 设计文档增加XXX评审项                                      │
│   │     └─ 对XXX接口增加防御性校验                                    │
│   └─ 流程改进（需要推动）                                            │
│         ├─ 推动建立XXX场景设计规范                                   │
│         ├─ 推动在设计阶段增加XXX评审环节                              │
│         └─ 推动将XXX纳入新人培训体系                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 2.3 代码规范对照分析（★★★★★重点）

### 2.3.1 目的

通过对照**浩鲸Java编码规范**，检查代码变更是否符合规范要求，找出违反规范的代码作为根因切入点。

### 2.3.2 代码变更数据获取

| 接口 | 用途 |
|------|------|
| `POST /rpc/v3/task-branch/{taskNo}/commit-range` | 获取代码分支Commit历史 |
| `POST /rpc/v3/task-branch/{taskNo}/changes/content` | 获取代码变动详细内容（Diff） |

### 2.3.3 代码规范检查维度

| 规范类别 | 关键检查点 | 对应规范编号 |
|---------|-----------|-------------|
| **集合处理** | subList强转ArrayList、Map视图修改、ConcurrentModificationException | J000001-J000010 |
| **并发处理** | 单例线程安全、线程安全集合、高并发下的Calendar/DateFormat | J000014, J000114-J000127 |
| **资源管理** | try-with-resources、资源关闭异常处理 | J000127 |
| **异常处理** | 异常捕获后未处理、异常丢失、异常类型选择不当 | 安全篇 |
| **日志规范** | System.out使用、日志级别选择、敏感信息泄露 | 安全篇 |
| **SQL安全** | SQL注入、预编译使用、查询条件有效性 | J000112 |
| **内存管理** | 大对象创建、内存泄漏、OutOfMemoryError | J000107-J000113 |

### 2.3.4 代码Diff归因分析流程

```
获取代码变更(Diff)
    ↓
解析变更文件列表
    ↓
逐文件检查关键代码模式
    ↓
对照规范检查
    ├─ 集合操作：是否有可能触发ConcurrentModificationException？
    ├─ 字符串处理：是否有字符串拼接性能问题？
    ├─ 异常处理：catch后是否正确处理？
    ├─ 资源关闭：是否使用try-with-resources？
    ├─ 并发安全：是否有多线程共享变量问题？
    └─ SQL安全：是否有SQL注入风险？
    ↓
违规代码定位
    ↓
根因归类
    ├─ 规范违反型：明确违反编码规范的代码
    ├─ 最佳实践型：未采用更优实践的代码
    └─ 业务逻辑型：规范没问题但业务逻辑有缺陷
    ↓
输出：违规代码片段 + 违反的规范条目 + 改进建议
```

- 分类：{devCatalog} > {devCatalogDetail}

### 测试环节分析

- 原因：{testReason}
- 结论：{testConclusion}

### 5.2 问题分类Prompt

请对照**浩鲸Java编码规范**，检查代码变更是否符合规范：

**重点检查的代码模式**：

| 检查项 | 规范要求 | 风险描述 |
|-------|---------|---------|
| **集合操作** | J000009：禁止在遍历中remove/add元素 | 可能导致ConcurrentModificationException |
| **subList使用** | J000001：subList不可强转ArrayList | 可能触发ClassCastException |
| **Map视图修改** | J000003：不可修改keySet/values/entrySet返回的集合 | 触发UnsupportedOperationException |
| **单例模式** | J000014：单例对象及其方法必须线程安全 | 多线程下单例状态可能不一致 |
| **资源关闭** | J000127：使用try-with-resources确保资源关闭 | 可能产生资源泄漏 |
| **日期格式化** | 安全篇：禁止静态Calendar/DateFormat | 高并发下日期格式化异常 |
| **SQL拼装** | J000112：确保SQL查询条件有效性 | 可能导致SQL注入或大表扫描 |
| **字符串拼接** | J000120：合理使用字符串连接方式 | 性能问题 |

**代码Diff分析Prompt**：

```
## 代码Diff分析

请仔细分析以下代码变更，识别违反规范的问题：

### 代码变更详情
{codeChanges}

### 分析要求

1. **逐文件分析**：对每个变更文件进行分析
2. **识别问题代码模式**：
   - [ ] 集合遍历中是否有remove/add操作？
   - [ ] 是否有可能触发ConcurrentModificationException的代码？
   - [ ] 是否有单例模式且线程安全存疑？
   - [ ] 是否有资源（IO、数据库连接）未使用try-with-resources？
   - [ ] 是否有静态DateFormat/Calendar使用？
   - [ ] 是否有SQL字符串拼接？
   - [ ] 是否有异常被catch后未处理或异常丢失？

3. **输出违规代码片段**：
   - 文件路径和行号
   - 问题代码
   - 违反的规范编号和描述
   - 可能导致的后果

4. **根因判定**：
   - 如果发现违规代码，判断该违规是否是导致故障的直接原因或重要因素
   - 如果未发现违规，判断问题是否属于业务逻辑缺陷而非编码规范问题
```

### 4.3 深层根因挖掘

### 4.1 问题分类
请先判断问题属于哪一类：
- 【开发引入】代码逻辑错误、设计缺陷、接口问题
- 【测试泄露】用例设计遗漏、用例执行偏差
- 【需求问题】需求描述不清、确认不到位
- 【外部依赖】第三方服务、基础设施问题

### 4.3 深层根因挖掘
对于归因为"场景考虑不全"的分析，请继续追问：
1. **为什么没考虑到？**
   - 是设计阶段的问题？（设计文档、接口契约、状态机）
   - 是编码阶段的问题？（代码走查、防御性编程、异常处理）
   - 是测试阶段的问题？（用例设计方法、checklist、场景组合）

2. **哪个环节的checklist或流程可以发现这个问题？**
   - 设计评审checklist是否覆盖该场景？
   - 代码走查checklist是否要求验证状态转换？
   - 测试用例设计是否要求覆盖正向/逆向/边界路径？

3. **如果是开发引入，是什么导致了代码缺陷？**
   - 缺少防御性编程？
   - 缺少边界条件判断？
   - 缺少异常处理？
   - 缺少代码走查？

### 4.5 注意事项

1. **不要直接使用现有复盘结论**，而要以它为起点进一步追问
2. **每个根因必须有支撑证据**，不能凭空猜测
3. **改进措施必须可落地**，避免"加强注意"这类模糊表述
4. **如果确实无法挖掘更深根因**，请说明原因并给出可能的改进方向
```

## 5. 与现有故障复盘结论的对照机制

### 5.1 对照目的

不是为了使用现有结论，而是为了：
1. **验证完整性**：检查AI分析是否遗漏了重要维度
2. **学习改进**：从现有分析中学习业务特点
3. **校准输出**：确保分析结论与业务实际相符

### 5.2 对照方式

```
AI根因分析结果
    ↓
与现有复盘结论对比
    ├─ 维度对比：是否覆盖了现有分析的各个维度？
    ├─ 深度对比：是否挖掘出了更深层的根因？
    ├─ 改进措施对比：是否提出了更具可操作性的措施？
    ↓
差异分析
    ├─ 如果AI分析的根因更深：说明现有流程有改进空间
    ├─ 如果AI分析的根因与现有一致：确认该问题的根因可靠性
    └─ 如果AI分析发现新的根因：标注为"潜在改进点"
    ↓
最终输出：综合AI分析 + 现有结论的最优分析
```

## 6. 根因分类体系

### 6.1 大类体系

| 大类 | 说明 |
|-----|------|
| 研发环节 | 代码编写、逻辑设计相关问题 |
| 测试设计类 | 测试用例设计、覆盖相关问题 |
| 需求分析类 | 需求描述、确认相关问题 |
