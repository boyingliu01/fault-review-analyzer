# 故障聚类分析系统 V4 - 需求对齐文档（最终版）

## 1. 需求确认

### 1.1 原始需求

基于前期讨论，用户的核心需求是：

> **通过故障根因的聚类分析，持续找到需要重点关注的改进点，确保找到的根本原因可以通过具体措施优化和消除。**

### 1.2 需求补充与细化

根据最新沟通，需求进一步明确为：

#### 核心目标（按优先级排序）

1. **识别高频根因模式**（最重要）
   - 找出在整个公司范围内重复出现的故障模式
   - 识别高频的根因类型
   - 为后续改进工作提供数据支撑

2. **违规检测**（重点关注）
   - 检测故障是否违反公司研发规范
   - 违规类型根据现有规范文档确定
   - 违规本身作为根因分类的重要维度

3. **根因可落地性**（关键要求）
   - 根因分析必须能导出具体的改进措施
   - 拒绝不可落地的根因（如"场景考虑不足"、"测试遗漏"等模糊描述）
   - 改进措施不需要指定责任人，但必须具体可执行

## 2. 根因分类体系

### 2.1 根因生长策略

**原则**：根因分类不是预制的，而是从数据中"生长"出来的

**生长机制**：
1. LLM根据故障信息自动分析根因
2. 对相似根因进行语义聚类
3. 从聚类结果中提取高频根因模式
4. 人工审核和确认根因分类
5. 持续迭代优化根因分类体系

### 2.2 根因大类（框架性分类）

仅作为根因分析的框架，具体子类由数据生长：

| 大类 | 说明 | 典型场景 |
|-----|------|---------|
| **违规类** | 违反公司研发规范 | 违反Java编码规范、违反数据库设计规范、违反安全规范等 |
| **需求类** | 需求相关问题 | 需求不明确、需求变更、需求遗漏等（需具体化） |
| **设计类** | 设计相关问题 | 架构设计缺陷、接口设计问题、性能设计不足等（需具体化） |
| **开发类** | 开发实现问题 | 代码逻辑错误、边界处理不当、异常处理缺失等（需具体化） |
| **测试类** | 测试相关问题 | 测试覆盖不足、测试场景遗漏、测试环境差异等（需具体化） |
| **运维类** | 运维部署问题 | 配置错误、部署问题、监控缺失、应急预案不足等（需具体化） |
| **环境类** | 环境相关问题 | 生产环境差异、依赖服务故障、网络问题等（需具体化） |
| **第三方类** | 外部依赖问题 | 第三方服务故障、接口变更、版本兼容等（需具体化） |

## 3. 根因可落地性标准

### 3.1 不可接受的根因（必须重新分析）

以下类型的根因被视为不可落地，需要LLM重新分析：

| 不可接受类型 | 示例 | 原因 |
|------------|------|------|
| 过于笼统 | "场景考虑不足"、"测试遗漏" | 无法确定具体改进方向 |
| 推卸责任 | "沟通不畅"、"协作问题" | 无法量化改进措施 |
| 表面原因 | "代码bug"、"配置错误" | 未触及根本原因 |
| 不可控因素 | "时间紧迫"、"资源不足" | 无法通过措施消除 |

### 3.2 可落地根因的标准

可落地的根因必须满足以下条件：

1. **具体性**
   - 明确指出问题发生的具体环节
   - 描述具体的技术或流程缺陷
   - 举例："订单状态机设计未考虑并发场景"而非"设计问题"

2. **可改进性**
   - 可以通过技术或流程改进消除
   - 改进措施明确且可执行
   - 举例："增加订单状态的乐观锁机制"而非"加强设计评审"

3. **可验证性**
   - 改进效果可以被验证
   - 有明确的验收标准
   - 举例："通过压测验证并发处理能力提升至1000TPS"而非"提升系统性能"

4. **可归因性**
   - 可以归属到具体的技术领域
   - 可以关联到具体的规范或最佳实践
   - 举例："违反Java并发编程规范第X条"而非"代码质量问题"

### 3.3 改进措施生成要求

对于每个可落地的根因，必须生成：

1. **具体措施描述**
   - 明确要做什么
   - 具体的技术方案或流程调整
   - 避免模糊的"加强"、"完善"等词汇

2. **验收标准**
   - 如何验证改进措施已落实
   - 具体的指标或检查点
   - 可量化的验收条件

3. **预期影响**
   - 预计能解决的问题
   - 预期效果（定量或定性）

**不需要**：责任人、时间节点（由管理层后续确定）

## 4. 分析流程确认

### 4.1 两阶段分析流程

```
┌─────────────────────────────────────────────────────────────────────┐
│                         阶段一：数据准备                              │
│                     （只需执行一次，可增量更新）                        │
├─────────────────────────────────────────────────────────────────────┤
│  1. 从API获取故障单详细信息                                           │
│  2. 提取关键信息（需求、设计、实现、测试、运维等）                       │
│  3. 【违规检测】基于规范知识库检测违规                                   │
│  4. 【根因分析】使用LLM深度分析根因（如果未违规或需补充分析）             │
│  5. 【根因验证】验证根因可落地性，生成改进措施                           │
│  6. 【向量化】将分析结果文本向量化                                      │
│  7. 【存储】保存到Chroma向量数据库                                      │
└─────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────┐
│                         阶段二：聚类分析                              │
│                     （可重复执行，参数可调）                            │
├─────────────────────────────────────────────────────────────────────┤
│  1. 【加载】从Chroma加载所有向量数据                                    │
│  2. 【聚类】使用HDBSCAN/层次聚类/K-Means进行聚类                        │
│  3. 【统计】统计各类根因频率，识别高频根因                               │
│  4. 【推荐】针对高频根因生成专项改进措施                                 │
│  5. 【可视化】生成根因分布图、违规分布图、改进措施追踪图、UMAP散点图        │
│  6. 【交互】支持相似度查询、参数调整、结果探索                           │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.2 违规检测流程

```
故障信息
    │
    ▼
┌─────────────────┐
│ 提取技术栈信息   │  ← 从故障单中提取使用的技术（Java、Oracle等）
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 匹配相关规范     │  ← 根据技术栈匹配对应的规范文档
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ LLM违规检测      │  ← 使用LLM对比故障信息与规范条款
└────────┬────────┘
         │
         ▼
    ┌────┴────┐
    ▼         ▼
┌───────┐  ┌───────────┐
│ 违规   │  │ 未违规     │
└───┬───┘  └─────┬─────┘
    │            │
    ▼            ▼
┌──────────┐  ┌──────────────┐
│记录违规   │  │继续根因分析   │
│类型和条款 │  │（非违规类）   │
└──────────┘  └──────────────┘
```

```

        ▼

    ▼         ▼
┌───────┐  ┌───────────┐

└──────────┘  └──────────────┘
```

## 5. 可视化需求确认

### 5.1 必须的可视化（P0）

| 可视化类型 | 用途 | 展示内容 |
|-----------|------|---------|
| **根因分布图** | 识别高频根因 | 按频率排序的柱状图，显示各类根因的故障数量和百分比 |
| **违规类型分布图** | 了解违规情况 | 饼图或柱状图，显示各类违规的分布 |
| **改进措施追踪图** | 跟踪改进措施 | 按优先级分组的柱状图，显示改进措施和预期影响 |
| **UMAP散点图** | 查看故障分布 | 2D散点图，按根因分类着色，悬停显示故障详情 |

### 5.2 增强的可视化（P1）

| 可视化类型 | 用途 | 展示内容 |
|-----------|------|---------|
| **相似度热力图** | 查看故障间相似性 | 按根因分类排序的相似度矩阵 |
| **层次聚类树状图** | 查看聚类层次 | 树状图展示聚类结构 |
| **3D散点图** | 多角度查看分布 | 3D散点图，支持旋转 |

### 5.3 交互功能需求

1. **参数调整**
   - 聚类算法选择（HDBSCAN/层次聚类/K-Means）
   - 聚类参数调整（min_cluster_size、距离度量等）
   - 实时查看聚类结果变化

2. **相似度查询**
   - 选择某个故障单
   - 查看与其最相似的N个故障单
   - 显示相似度分数

3. **结果探索**
   - 点击散点图上的点查看故障详情
   - 筛选特定类型的故障
   - 导出聚类结果

## 6. 技术选型确认

### 6.1 已确认的技术选型

| 组件 | 选择 | 理由 |
|-----|------|------|
| **向量数据库** | Chroma | 本地持久化、简单易用、与LangChain集成好 |
| **Embedding模型** | Volcano Engine doubao-embedding-vision-251215 | 多模态模型、支持文本、性能良好 |
| **LLM模型** | Volcano Engine doubao-seed-1-8-251228 | 支持长文本、性价比高 |
| **聚类算法** | HDBSCAN（主）+ 层次聚类 + K-Means | HDBSCAN适合噪声数据、无需预设聚类数 |
| **相似度计算** | 余弦相似度 | 适合文本向量、计算简单 |
| **降维可视化** | UMAP | 保持局部结构、适合高维数据可视化 |
| **Web界面** | Streamlit | 快速开发、适合数据科学应用 |

### 6.2 新增组件

| 组件 | 用途 | 技术方案 |
|-----|------|---------|
| **规范知识库** | 存储和管理规范 | JSON文件 + Python类 |
| **违规检测器** | 检测违规 | LLM + 规则匹配 |
| **根因验证器** | 验证根因可落地性 | 规则引擎 + LLM |
| **根因统计器** | 统计高频根因 | Python数据分析 |
| **改进措施推荐器** | 生成改进措施 | LLM + 模板 |
