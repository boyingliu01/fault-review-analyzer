# 故障聚类分析系统 V3 - 需求对齐文档（修订版）

## 1. 原始需求回顾与补充

### 1.1 核心目标（修订）

**原始目标**：
- 使用大模型进行深度故障根因分析
- 实现故障单的智能聚类，发现相似故障模式
- 提供可视化展示，帮助理解聚类结果
- 支持交互式分析，探索故障间关系

**补充的核心目标**：
- ✅ **违规检测**：重点检测故障是否违反公司研发规范，违规本身应作为根因分类
- ✅ **根因可落地性**：根因分析必须能导出具体的改进措施，能够消除问题
- ✅ **持续改进导向**：通过聚类找到高频根因，推进专项改进措施，持续减少故障

### 1.2 关键业务逻辑

#### 1.2.1 违规检测逻辑
```
故障信息 + 公司研发规范 → 违规检测 → 违规根因分类
```

**违规根因分类示例**：
- 违反Java代码规范
- 违反C++代码规范
- 违反数据库开发规范
- 违反数据库运维规范
- 违反测试规范
- 违反发布规范
- 违反代码评审规范

**业务规则**：
- 违规是最高优先级的关注点
- 遵循规章制度应该能规避大部分基础错误
- 复盘分析必须重点关注违规现象

#### 1.2.2 根因可落地性逻辑
```
根因分析 → 检查可落地性 → 生成改进措施
```

**可落地性判断标准**：
- ✅ 能否制定具体的改进措施？
- ✅ 能否明确责任人和时间节点？
- ✅ 能否验证改进效果？
- ✅ 能否从根本上消除问题？

**不可落地根因示例**：
- ❌ "场景考虑不足" - 无法制定具体措施
- ❌ "测试遗漏" - 太宽泛，无法落实
- ❌ "设计缺陷" - 不够具体

**可落地根因示例**：
- ✅ "违反Java代码规范-未进行空指针检查" - 可以制定规范培训、代码检查工具
- ✅ "违反数据库开发规范-未添加索引" - 可以制定索引规范、自动化检查
- ✅ "违反测试规范-未覆盖边界条件" - 可以制定测试用例模板

#### 1.2.3 持续改进逻辑
```
聚类分析 → 根因统计 → 识别高频根因 → 推进专项改进 → 验证效果
```

**改进流程**：
1. 通过聚类分析发现高频根因
2. 按频率排序，识别Top N根因
3. 针对每个高频根因制定专项改进措施
4. 实施改进并验证效果
5. 持续监控，形成闭环

## 2. 系统架构调整

### 2.1 原架构问题分析

**原架构**：
```
故障信息 → LLM分析 → 向量化 → 聚类 → 可视化
```

**存在的问题**：
1. ❌ LLM分析未包含规范比对逻辑
2. ❌ 根因分类不够细致，无法区分违规类型
3. ❌ 缺少根因可落地性验证
4. ❌ 缺少改进措施生成
5. ❌ 聚类目标不明确，未聚焦高频根因发现

## 3. 核心功能需求（修订）

### 3.1 规范知识库管理

**需求描述**：
- 存储公司各类研发规范
- 支持规范的增删改查
- 支持规范的版本管理
- 支持规范的分类（代码规范、数据库规范、测试规范等）

**数据结构**：
```python
class Standard(BaseModel):
    standard_id: str
    category: str  # 代码规范/数据库规范/测试规范等
    sub_category: str  # Java/C++/MySQL等
    title: str
    content: str  # 规范内容
    version: str
    effective_date: datetime
    status: str  # active/deprecated
```

### 3.2 违规检测引擎

**需求描述**：
- 基于规范知识库检测故障是否违规
- 识别具体的违规类型
- 提供违规证据
- 计算违规置信度

**检测逻辑**：
```
故障信息 + 规范知识库 → LLM分析 → 违规检测结果
```

**输出格式**：
```python
class ViolationDetection(BaseModel):
    has_violation: bool
    violation_type: str | None  # 违反Java代码规范等
    violation_detail: str | None
    violated_standard_id: str | None
    confidence: float  # 0-1
    evidence: list[str]  # 违规证据
```

### 3.3 根因可落地性验证

**需求描述**：
- 验证LLM分析的根因是否可落地
- 如果不可落地，要求重新分析
- 生成可落地性评分

**验证标准**：
1. 能否制定具体的改进措施？
2. 能否明确责任人和时间节点？
3. 能否验证改进效果？
4. 能否从根本上消除问题？

**输出格式**：
```python
class RootCauseValidation(BaseModel):
    root_cause: str
    is_actionable: bool
    actionability_score: float  # 0-1
    improvement_measures: list[str]
    responsible_person: str | None
    timeline: str | None
    validation_method: str | None
```

### 3.4 高频根因识别

**需求描述**：
- 统计各类根因的出现频率
- 按频率排序，识别Top N根因
- 提供根因趋势分析（按时间）
- 提供根因占比分析

**输出格式**：
```python
class RootCauseStatistics(BaseModel):
    root_cause: str
    count: int
    percentage: float
    trend: str  # increasing/decreasing/stable
    top_faults: list[int]  # 该根因对应的故障ID
```

### 3.5 改进措施生成

**需求描述**：
- 针对每个根因生成具体改进措施
- 明确责任人和时间节点
- 提供改进措施优先级
- 提供改进效果预估

**输出格式**：
```python
class ImprovementMeasure(BaseModel):
    measure_id: str
    root_cause: str
    description: str
    priority: str  # high/medium/low
    responsible_person: str
    timeline: str
    expected_impact: str
    validation_criteria: list[str]
    status: str  # pending/in_progress/completed
```

## 5. 关键决策点

### 5.1 违规检测时机

**问题**：违规检测应该在向量化之前还是之后？

**推荐方案**：**在向量化之前进行**

**理由**：
1. 违规信息是关键特征，应该包含在向量化文本中
2. 违规检测结果会影响根因分类，进而影响聚类结果
3. 违规信息可以作为元数据存储，便于后续过滤和查询
4. 违规检测结果需要人工审核，应该在早期进行

### 5.2 根因分类体系

**问题**：如何设计根因分类体系？

**推荐方案**：**分层分类体系**

**第一层（大类）**：
1. 违规类
2. 需求类
3. 设计类
4. 开发类
5. 测试类
6. 运维类

**第二层（子类）**：
- 违规类：
  - 违反Java代码规范
  - 违反C++代码规范
  - 违反数据库开发规范
  - 违反数据库运维规范
  - 违反测试规范
  - 违反发布规范
  - 违反代码评审规范
- 开发类：
  - 代码逻辑错误
  - 边界条件处理不当
  - 并发处理问题
  - 性能问题
  - 安全漏洞
- 测试类：
  - 测试用例不完整
  - 边界条件未覆盖
  - 异常场景未测试
  - 测试环境差异

### 5.3 根因可落地性验证

**问题**：如何确保根因可落地？

**推荐方案**：**LLM + 规则验证**

**验证流程**：
1. LLM分析根因并生成改进措施
2. 规则引擎检查改进措施是否具体
3. 如果不可落地，要求LLM重新分析
4. 人工审核最终结果

**规则示例**：
- 改进措施必须包含动词（如"添加"、"修改"、"优化"）
- 改进措施必须明确责任人或角色
- 改进措施必须包含时间节点
- 改进措施必须包含验证方法
